# Automotive SPICE（ASPICE）工程实践

状态：Draft（过程编号、要求和能力等级需按适用 PAM 版本确认）

## 1. 核心思路
ASPICE 不是文档数量检查。工程实施重点是过程是否有定义、工作是否执行、产物是否满足要求、过程间是否可追溯，以及是否存在客观证据。项目采用的过程、裁剪规则和评估模型版本应在项目质量计划中明确。

## 2. 常见系统/软件工程链路
客户/系统需求 → 系统架构 → 系统集成与验证 → 软件需求 → 软件架构 → 软件详细设计与实现 → 软件单元验证 → 软件集成与验证 → 软件验证。

具体过程编号、名称和适用范围应对照项目采用版本的 PAM，不应仅凭记忆认定条款。

## 3. 工作产品之间的追溯
| 上游产物 | 下游产物 | 需要证明什么 |
|---|---|---|
| 系统需求 | 系统架构 | 需求由架构元素分配或实现 |
| 系统架构 | 系统集成测试 | 接口、交互和系统行为被验证 |
| 软件需求 | 软件架构 | 需求有架构分配和设计依据 |
| 软件架构 | 详细设计/代码 | 实现路径可追踪 |
| 详细设计/代码 | 单元测试 | 关键逻辑和边界有验证证据 |
| 需求/风险控制 | 测试用例与结果 | 预期行为和风险控制得到验证 |

追溯不仅要有链接，还要检查链接方向、覆盖率、变更影响和验证结果。

## 4. 评审证据清单
- 评审输入及版本明确
- 评审标准和参与角色明确
- 问题、决议、责任人和截止日期可追踪
- 问题关闭有证据，而不只是状态改为 Closed
- 重大变更有影响分析和回归验证
- 基线、配置和版本可复现
- 未解决问题与风险有记录和处置策略

## 5. 与功能安全和失效分析结合
将安全需求链接到系统/软件需求和设计元素；将安全机制映射到失效模式、诊断策略和验证用例；通过故障注入、边界测试或分析证据验证安全机制；对需求变更执行影响分析，检查风险分析、设计、测试和安全论证是否同步更新。

ASPICE 与 ISO 26262 的目标和评价方式不同；二者可以共享工作产品和追溯关系，但不能相互替代。

## 6. 常见过程薄弱点
- 需求写成实现方案，缺少可验证条件
- 追溯关系存在，但无法证明下游真正实现上游需求
- 测试只验证正常路径，缺少边界、异常和恢复路径
- 评审记录没有问题闭环或版本信息
- 变更后没有系统性回归和影响分析
- 过程模板齐全，但实际项目没有客观执行证据

## 7. 建议的轻量级项目看板
每条需求记录 ID、版本、来源、验证标准、架构分配、设计链接、测试用例、测试结果、缺陷、变更影响和审核状态。

## 8. 依据
正式评估前，核对项目适用的 Automotive SPICE PAM 版本、组织过程裁剪、评估范围和工作产品特征。本文是实践性概述，不作为对特定能力等级的符合性声明。
