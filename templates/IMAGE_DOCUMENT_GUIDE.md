# 图文技术文档制作规范

状态：Draft（适用于个人技术知识库）

## 1. 目标

以 Markdown 作为主文档，将原理图、系统架构图、通信时序图、状态机、波形和测试截图嵌入正文。图像文件独立保存，便于 GitHub 网页展示、版本管理和 ChatGPT 检索文字说明。

## 2. 推荐目录

```text
主题目录/
├── TOPIC.md
└── images/
    ├── topic-system-architecture.png
    ├── topic-sequence.svg
    └── topic-test-waveform.png
```

图片应优先放在对应主题目录下的 `images/` 子目录，不建议将所有图片混放在仓库根目录。

## 3. 在 Markdown 中插图

图片与 Markdown 文件位于同一主题目录时，使用相对路径：

```markdown
![图 1：系统架构图](images/topic-system-architecture.png)

**图 1：系统架构图。** 说明图中模块边界、关键接口和数据/能量流向。
```

每张重要图片应包含：
- 图号和准确图名
- 图片表达的结论或阅读重点
- 关键模块、信号、状态或参数解释
- 对应需求、标准、代码版本或测试记录（如适用）
- 图片来源与审核状态

## 4. 图片格式选择

| 类型 | 推荐格式 | 注意事项 |
|---|---|---|
| 架构图、流程图、状态机 | SVG 或 PNG | SVG 适合线条与文字；确保字体和标签清晰 |
| 电路图、波形图、示波器截图 | PNG | 保留坐标、单位、通道标注和测试条件 |
| 扫描页、照片 | PNG/JPEG | 需要补充来源、页码或拍摄条件 |
| 大型原始测试资料 | 原文件或压缩包另行归档 | Markdown 中链接到资料，不要用截图代替原始证据 |

## 5. 文件命名

建议使用小写英文、数字和连字符，避免空格及过长名称，例如：
- `evcc-system-architecture.png`
- `dc-v2h-sequence.svg`
- `mosfet-switching-waveform.png`
- `fmea-fault-chain.png`

## 6. 图文技术内容的可信度

- AI 生成图用于解释概念时，标注“概念示意图”，不可作为规范原文或实测证据。
- 标准时序、引脚定义、协议字段和安全要求必须对照项目适用的正式标准与设计输入复核。
- 测试波形应注明测试对象、软硬件版本、仪器/探头、工况、单位及结论；不可用生成图片冒充实测结果。
- 代码截图不应替代可检索的源代码。
- 导入前确认图片不包含密码、令牌、客户信息、公司机密或未获授权披露的专利内容。

## 7. 插图验收清单

- [ ] 图片已提交到仓库，且路径大小写完全一致
- [ ] GitHub 网页能正常渲染图片
- [ ] 图片在正文中有图号、图名和解释
- [ ] 图片中的文字、单位、箭头与信号方向可读
- [ ] 正式标准结论有可追溯来源
- [ ] 概念图与真实测试证据有明确区分
- [ ] 图片未泄露敏感信息
- [ ] 文件名、目录和索引链接符合约定

## 8. 图片导入流程

1. 将此前生成或用户提供的图片上传到当前对话。
2. 确认图片主题、文件名、来源和是否允许存入此仓库。
3. 将图片文件加入相应的 `images/` 目录。
4. 修改对应 Markdown，使用相对路径嵌图并添加工程解读。
5. 在 GitHub 网页打开文档，检查图像显示与链接。
6. 在 ChatGPT GitHub 连接器中测试是否能检索到图旁的文字说明。

## 9. 统一归档流水线（全库适用）

### 9.1 标准目录与命名
- 每个主题文档在同级建立 `images/`，图片与使用它的文档尽量放在同一主题目录。
- 文件名采用小写英文、数字和连字符；建议格式：`主题-内容-图型.扩展名`，例如 `aspice-process-mindmap.png`。
- 支持的常用格式：PNG、JPG/JPEG、WEBP、GIF、SVG。技术图优先 PNG/SVG；动图仅在确有价值时使用。
- 在 Markdown 中使用相对路径，禁止依赖临时会话链接或需要登录的临时下载链接。

### 9.2 每次归档的最小步骤
1. 生成或取得图片文件本体。
2. 按主题保存到对应的 `images/` 目录。
3. 在对应 Markdown 插入相对路径图片引用，并补充图名、用途、关键结论和复核状态。
4. 提交到 GitHub。
5. 由自动化检查确认引用路径存在、图片文件有引用；对有意保留但未嵌入的素材，应在提交说明中说明原因。

### 9.3 自动检查
仓库中的 GitHub Actions 工作流会在 Pull Request 和推送到 `main` 时运行资产引用检查：
- 检查 Markdown 中本地图片引用是否指向存在的文件。
- 检查 Markdown 正文中的本地文件/目录链接是否存在。
- 忽略围栏代码块中的示例语法，避免把文档示例误判为真实引用。
- 检查 images 目录下未被 Markdown 引用的图片，提示可能遗漏。
- 若发现真实断链，工作流失败，修复后再合并。

相关脚本：`scripts/check_image_refs.py`（图片引用检查并调用链接检查）、`scripts/check_markdown_links.py`（本地 Markdown 链接检查）。

自动检查只验证文件和引用关系，不会判断 AI 图片中的技术内容是否正确，也不会自动把 ChatGPT 对话中生成的图片传输到 GitHub。图片二进制数据仍需通过支持文件上传的入口或本地自动化脚本送入仓库。

### 9.4 安全与工程质量门禁
- 不提交 API Token、密码、客户个人信息或未授权材料。
- AI 生成的技术图应标注“概念示意图”；标准字段、引脚、时序、安全要求必须对照正式资料复核。
- 真实测试波形与 AI 概念图必须区分，不得将生成图冒充实测证据。
- 对重要图片建议记录来源、日期、适用版本、审核人/状态。

## 10. 减少手动操作：本地导入或 GitHub 自动归档

### 10.1 本地命令

在已克隆的本地仓库中运行：

```bash
python scripts/import_knowledge_image.py "/path/to/aspice-mindmap.png" "03-工程开发方法/ASPICE/README.md" --title "ASPICE 全流程思维导图"
```

如需同时在本地创建 Git 提交，可追加 `--commit`，检查后再推送。

### 10.2 GitHub 自动归档

将图片文件和同名 JSON 元数据一起提交到：

`06-创新、扩展与职业竞争/技术图片资产库/待归档/`

JSON 最少包含：

```json
{
  "title": "EVCC 系统架构概念图",
  "document": "04-充电系统与产品/EVCC/README.md",
  "source": "AI-generated concept illustration",
  "status": "Draft"
}
```

推送后，`.github/workflows/auto-archive-technical-images.yml` 会自动验证队列、将图片移入目标 Markdown 同级的 `images/`、插入图片引用和说明、更新技术图片资产索引，并提交归档结果。也可以在 GitHub Actions 页面手动运行该工作流。

限制：目标 Markdown 必须已经存在；支持 PNG、JPG/JPEG、WEBP、GIF、SVG；单张图片最大 20 MiB；不覆盖同名目标文件。每张图片都必须有同名 JSON 元数据，且 `document` 路径必须在仓库内。

### 10.3 验收与安全

- 图片/链接检查工作流必须通过。
- 检查图片是否正常渲染、文字与单位是否正确。
- AI 生成图默认标记为 Draft/概念示意，不得冒充标准原图或实测证据。
- 不提交密码、令牌、客户信息或未获授权披露的资料。
