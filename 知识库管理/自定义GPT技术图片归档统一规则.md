# 自定义 GPT 技术图片生成与 GitHub 归档统一规则

适用范围：本仓库全部技术主题、技术文档与后续生成的技术图片。目标是让图片生成、归档、Markdown 插入、索引更新和验证遵循同一套可追溯规则。

## 1. 执行原则

1. 先确定目标，再写文件。优先更新已有主题文档；通过仓库目录树和文件内容确认路径真实存在。用户明确指定文档时以指定路径为准。无法唯一确定目标时，只询问一个必要问题，不得猜造路径。
2. 优先 SVG 源码直写。架构图、流程图、状态机、时序图、思维导图、技术知识卡片等优先生成有效 SVG XML 文本，并通过 GitHub 文件接口写入 .svg。
3. 位图必须是真实字节。PNG/JPG/JPEG/WEBP/GIF 只能上传真实文件字节；不得把 URL、说明文字、SVG 源码或伪造 Base64 存成位图扩展名。
4. 先新增，不覆盖。归档前检查目标文件名是否存在。存在时生成有意义的新文件名，不得静默覆盖已有资产。
5. 技术真实性优先。不编造标准条款号、参数、测试结果或合规结论。资料不足时在图和文档中明确标注“概念示意/待核对”。
6. 状态必须真实。AI 生成图默认 Draft。只有完成技术人工核对后才可标为 Reviewed；只有满足项目正式审批要求并有可追溯审批依据时才可标为 Approved。GPT 不得自行宣称完成了人工审核。
7. 提交后必须读回验证。文件写入成功不等于流水线成功；必须重新读取目标文件、Markdown、索引，并检查 GitHub Actions 实际运行结果。未确认的步骤明确标注未验证。

## 2. 统一存储位置

### 2.1 主题专用图片

存放在目标 Markdown 同目录下的 images 子目录。例如：

    04-充电系统与产品/充电系统/协议与时序/
    ├── ISO15118.md
    └── images/
        └── iso15118-dc-v2h-workflow.svg

Markdown 使用相对路径引用：

图片引用写法：使用标准 Markdown 图片语法，将目标文件名写成相对于该文档的 images/文件名.svg 路径；此处仅说明规则，不引用实际资产。

### 2.2 跨主题复用图片

统一登记在 [技术图片资产库](../06-创新、扩展与职业竞争/技术图片资产库/README.md)。若同一图片需要被多个主题复用，不要复制出多个不一致版本；优先保留一个权威资产，并从其他文档相对引用该资产。

### 2.3 自动归档队列

自动归档时，将图片和同名 JSON 元数据一起提交至：

    06-创新、扩展与职业竞争/技术图片资产库/待归档/

例如：

    待归档/
    ├── iso15118-dc-v2h-workflow.svg
    └── iso15118-dc-v2h-workflow.json

GitHub Actions 会校验元数据、把图片移动到目标文档旁的 images 目录、插入 Markdown 图片和图示说明、更新资产库归档记录，再执行链接检查。归档后队列应清空；不得把临时文件或 Python 字节码提交进仓库。

## 3. 文件命名规则

- 使用小写英文、数字和连字符；扩展名使用真实格式。
- 文件名应表达技术主题与图种，例如 evcc-state-machine.svg、dc-v2h-sequence.svg、mosfet-buck-switching.svg。
- 避免 image1.svg、final-final.svg、日期堆叠和空泛名称。
- 不覆盖同名文件。版本差异显著时可使用 -v2 或明确的标准版本后缀。
- 文件名不得包含用户隐私、访问令牌、账号标识或其他敏感信息。

## 4. 自动归档元数据

每个待归档图片必须有一个同名 JSON 文件。最小格式如下：

    {
      "title": "ISO 15118-20 DC V2H 系统与通信协同示意图",
      "document": "04-充电系统与产品/充电系统/协议与时序/ISO15118.md",
      "source": "AI-generated conceptual engineering diagram; verify against the applicable ISO 15118-20 edition and system design",
      "status": "Draft",
      "filename": "iso15118-dc-v2h-workflow.svg"
    }

字段规则：

- title：必填，简洁、准确、中文优先。
- document：必填，仓库内已存在的 Markdown 文件路径，使用仓库相对路径，不以斜杠开头。
- source：建议填写。标明 AI 生成、人工绘制、代码生成或外部来源；外部来源应记录 URL 和许可信息。
- status：建议填写，默认 Draft。
- filename：可选；若填写，必须是单一文件名，不能含目录路径，扩展名须与真实文件格式一致。
- 图片和元数据基名必须相同，例如 diagram.svg 与 diagram.json。
- 当前归档脚本支持 PNG、JPG/JPEG、WEBP、GIF、SVG，单张图片最大 20 MiB。

## 5. 技术图绘制规则

1. 使用清晰的标题、合理画布比例、留白与统一字体；中文使用常见中文字体栈。
2. 架构图要区分系统边界、硬件/软件组件、接口和数据流；时序图要清晰标注参与者、消息方向与先后关系；状态机要标注状态、触发条件和转换；电路图要核对器件极性、参考方向、单位和关键参数。
3. 使用颜色时必须提供语义图例；不能仅依赖颜色表达安全关键含义。
4. 图中标准编号和版本需可追溯；不确定时写“版本待核对”，不得猜测条款号。
5. 概念图不能伪装成标准原图、真实测试波形、实测数据或认证输出。
6. SVG 应包含有效的 svg 根元素、合理的 viewBox，并尽可能提供 title 与 desc。避免脚本、外部依赖和不必要的远程资源。

## 6. Markdown 插入规则

- 在目标文档中优先复用现有“图片资料”章节；若没有该章节，在文档末尾新增。
- 插入标准 Markdown 图片语法，路径必须相对于目标文档所在目录。
- 图片下方必须有图示说明，至少说明图名、用途或主要结论、来源和审核状态；重要技术图还要注明关键假设与待核对事项。
- 不要把完整 SVG 源码塞进 Markdown 正文，也不要把临时沙盒链接当作永久资源。
- 不重复插入同一图片引用；如文档已有相同图片，应先检查并更新现有说明，而不是再次追加。

## 7. 必须执行的端到端验证

按顺序逐项验证，不能用“已提交”替代“已验证”：

1. 目标核对：目标 Markdown 在仓库中存在，路径与用户意图一致。
2. 文件核对：图片文件已创建，格式和扩展名一致；SVG 可读回为完整 UTF-8 文本。
3. 元数据核对：队列模式下图片和 JSON 同名、JSON 可解析，document 指向现存 Markdown。
4. 归档核对：图片已出现在目标文档旁的 images 目录；同名冲突没有被覆盖。
5. 文档核对：重新读取 Markdown，确认图片引用和说明只出现一次，且相对路径解析正确。
6. 索引核对：重新读取资产库 README，确认归档记录指向正确文档和图片。
7. 队列核对：已成功归档的图片和 sidecar 不再留在待归档队列。
8. 自动化核对：检查对应 GitHub Actions run 的最终状态和失败步骤；只有结论为 success 才能报告工作流通过。
9. 渲染核对：若能实际访问 GitHub 页面，检查图片渲染与可读性；若未检查，明确说明“尚未验证视觉渲染”。
10. 仓库卫生核对：不留下 __pycache__、.pyc、临时文件、凭据或其他无关产物。

报告结果时分别列出“已完成”“验证通过”“尚未验证”，不得将它们混为一谈。

## 8. 自定义 GPT 可直接执行的规则

当用户要求生成技术图片并归档到本知识库时，严格执行：

1. 先检查仓库目录树，确认目标 Markdown 和图片目录；优先复用现有主题文档。
2. 若用户已指定目标文档，使用该文档；若有多个合理目标且影响归档位置，只问一个澄清问题。
3. 优先生成 SVG 源码。位图只有在能取得真实图片字节时才采用。
4. 检查目标文件是否已存在，绝不静默覆盖。
5. 创建图片及同名 JSON 元数据；元数据至少包含 title、document，并尽可能包含 source、status、filename。
6. 需要自动归档时，将二者提交到统一待归档目录，等待 Actions 完成；不得把图片直接放入队列以外的位置后又假称流水线完成。
7. 重新读取归档结果，确认目标图片、Markdown 引用、图示说明和资产索引。
8. 检查实际 Actions 运行记录。失败时读取日志、修复根因并再次验证；不能跳过检查或仅凭提交成功宣布通过。
9. 最终回复提供目标文档、图片文件和 Actions 的直接链接，并用简短清单报告归档与验证状态。
10. 不要把访问令牌、密钥、私有凭据写进文档、SVG、元数据或提交信息；不要将私有仓库内容发布到公共位置。
