# AUTOSAR 与汽车软件架构

状态：Draft（需按 Classic/Adaptive、版本和项目配置确认）

## 1. 架构分析的起点
先确认项目使用 AUTOSAR Classic Platform、Adaptive Platform，还是混合架构；不要将两者的运行机制、接口和部署方式混为一谈。对典型控制器软件，可从应用组件、运行时环境、基础软件和微控制器抽象层理解职责分工。

## 2. Classic Platform 概念分层
| 层/元素 | 主要职责 | 设计检查点 |
|---|---|---|
| Application SWC | 实现应用功能与控制逻辑 | 组件边界、可复用性、接口定义 |
| RTE | 提供 SWC 间及 SWC 与 BSW 的通信抽象 | 端口映射、数据一致性、调用方式 |
| Services | OS、诊断、通信、NVM 等服务 | 配置正确性、错误处理、资源限制 |
| ECU Abstraction | 抽象 ECU 外设及板级差异 | 驱动接口、硬件依赖 |
| MCAL | 微控制器外设驱动 | 芯片/版本、初始化、时序和诊断 |
| OS/BSW 配置 | 调度、任务、事件、通信与内存等 | 周期、优先级、栈、资源和超时 |

实际模块划分、服务配置和调用路径必须以项目生成配置和软件架构为准。

## 3. EVCC 类应用的功能分解示例
可按职责划分 Connection/CP Manager、PLC/Link Manager、Protocol Session Manager、Charge State Machine、Energy Limit Manager、Diagnostic Manager、Vehicle Interface Adapter、Logging/Measurement。该分解是功能示例，不意味着每个模块必须对应一个 SWC。

## 4. 接口契约必须写清楚
每个接口至少定义信号名、数据类型、单位、缩放和有效范围；生产者、消费者及数据所有权；更新周期、最大延迟和超时；初始值、无效值、替代值及数据新鲜度；并发访问和一致性要求；通信丢失、校验失败和恢复行为；安全等级、诊断要求和验证证据（若适用）。

## 5. 状态机与任务设计
- 明确周期任务、事件任务和运行到完成的调用路径。
- 评估最坏执行时间、任务优先级、栈、资源竞争与阻塞。
- 对状态机定义事件优先级、超时计时起点、重入规则和复位行为。
- 避免将“没有收到新数据”解释为“收到零值”。
- 对跨任务/跨 ECU 信号处理旧数据、无效数据和更新不同步。

## 6. 验证策略
- 单元测试：边界条件、错误输入、状态转移和分支
- 软件集成测试：接口映射、RTE/BSW 交互、配置和通信
- 软件验证：需求符合性、时序、资源与异常处理
- 故障注入：超时、无效值、通信丢失、诊断失败
- 静态分析与代码审查：编码规则、复杂度、未定义行为等
- 追溯：需求 → 架构/组件 → 详细设计/代码 → 测试用例 → 结果

## 7. 项目需补充的信息
AUTOSAR 平台与版本、ECU/编译器/MCU/OS/配置工具版本、SWC/端口/Runnable/Task/Event 映射、通信与诊断栈配置、时序预算、资源预算和安全需求。
