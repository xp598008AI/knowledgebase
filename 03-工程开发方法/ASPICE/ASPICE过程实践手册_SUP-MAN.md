# ASPICE 过程实践手册：SUP / MAN

> 状态：Draft / 项目实施参考。过程范围、编号和工作产品须按项目采用的 PAM/PRM 版本确认。本文为工程实践化说明，不是标准原文或正式评估规则。

## 1. 为什么 SUP / MAN 决定过程是否真正落地？

SYS/SWE 描述工程开发主链路；MAN（管理）负责让活动在范围、进度、资源、风险和协作约束下可执行；SUP（支持）负责让工作产品、质量检查、问题、配置和变更受控。没有这些机制，追溯和验证容易在项目压力下断裂。

## 2. MAN：项目管理实践

### 项目策划与监控

建议建立一套统一项目控制视图，至少包含：
- 工作范围、里程碑、交付物、责任人和依赖关系；
- 活动估算、资源计划、进度基线和实际完成情况；
- 风险/问题、应对措施、责任人、到期日和状态；
- 需求变更、接口变更、技术决策及其对范围/进度/资源的影响；
- 与客户、供应商和跨团队的沟通机制及决策记录。

**每周项目检查问题**
1. 哪些里程碑发生偏差？偏差依据是什么？
2. 是否有阻塞需求、接口、硬件样件、软件构建或测试环境的依赖？
3. 关键风险的概率/影响是否变化？缓解措施是否有效？
4. 新变更对范围、资源、计划、测试和交付有什么影响？
5. 逾期行动项是否升级处理，是否记录决策？

### 风险管理

风险记录建议字段：Risk ID、描述、原因、后果、概率、影响、优先级、应对策略、责任人、截止日期、触发条件、剩余风险和关闭依据。

风险和问题应区分：
- **风险**：未来可能发生的不确定事件；
- **问题/缺陷**：已经发生、需要处置的事实。

### 协作与接口管理

跨团队接口应定义提供方、使用方、接口内容、版本、交付时间、验收条件、变更通知和争议升级路径。会议纪要应记录决策与行动项，而不是只保留讨论流水账。

## 3. SUP：支持过程实践

### 质量保证（Quality Assurance）

**目标：** 对过程和工作产品进行有计划的客观检查，识别偏差并推动关闭。

建议做法：
1. 根据项目风险和里程碑制定 QA 检查计划。
2. 定义检查范围、准入条件、检查表版本和抽样方法。
3. 尽可能保持检查角色的客观性，并明确发现项升级路径。
4. 每项发现记录要求/规则、客观证据、风险、责任人、期限和关闭准则。
5. 由指定人员复核关闭证据，保留记录。

**QA 发现项最小字段**
- QA-ID、检查日期、对象/版本、过程或工作产品；
- 依据的要求/检查规则；
- 客观事实与证据链接；
- 偏差描述、风险等级、责任人、计划完成日期；
- 纠正措施、复核结论、关闭日期。

### 配置管理（Configuration Management）

配置管理不是“把文件放到 Git”，而是识别和控制对交付结果有影响的配置项，并能说明某次测试/发布究竟用了什么。

**配置项示例**
- 系统/软件/硬件需求、架构、详细设计；
- 源代码、模型、编译器/工具链配置；
- 标定参数、诊断数据库、通信数据库；
- 测试脚本、测试数据、环境配置；
- 生成物、测试报告、发布说明和已知问题清单。

**基线建立步骤**
1. 定义配置项、命名规则、所有者和存储位置。
2. 定义版本控制、访问权限和变更审批规则。
3. 在里程碑建立基线并记录基线清单。
4. 确保测试报告引用明确的代码/配置/环境版本。
5. 发布前核对源文件、构建产物、测试结果和发布说明一致。
6. 定期核查配置状态和未授权变更。

### 问题解决（Problem Resolution）

每个问题应有唯一 ID，并记录：
- 发现来源、现象、复现步骤、环境和影响版本；
- 严重度/优先级及分级依据；
- 临时措施、根因分析、纠正措施；
- 责任人、计划完成日期、修复版本；
- 回归范围、执行结果、关闭准则和复核人。

“已修复”不是充分的关闭证据。至少应能说明在哪个版本修复、如何验证、哪些相关功能需要回归。

### 变更管理（Change Management）

变更流程建议：

```text
提出变更 → 登记与初筛 → 影响分析 → 评审/批准
   → 更新需求/设计/代码/测试 → 执行验证与回归
   → 更新基线与发布信息 → 关闭变更
```

影响分析至少覆盖：
- 需求、架构、接口和详细设计；
- 代码、硬件、标定、诊断和通信数据库；
- 单元/集成/系统测试、回归范围和测试环境；
- 功能安全、网络安全、法规或供应商接口（按适用性）；
- 进度、成本、资源、交付物和客户批准。

### 文档与工作产品评审

评审前明确对象版本、目标、准入条件和检查表；评审中记录发现项；评审后追踪关闭和复核。避免无版本的“最终版”文件和无法证明参与/结论的会议记录。

## 4. 一条贯穿项目的变更案例

**情景：** EVCC 软件将通信状态机中的超时处理逻辑从单一计时器改为按状态独立配置。

影响分析至少检查：
1. 软件需求是否定义每个状态的超时条件和配置来源；
2. 软件架构/详细设计中的状态迁移、计时器启停与取消逻辑；
3. 配置参数、默认值、边界检查和诊断接口；
4. 单元测试的边界值、状态重入、复位、重复消息；
5. 集成测试中通信管理、诊断和状态控制的交互；
6. 系统测试和故障注入测试是否需要更新；
7. 代码、参数、测试脚本、报告和发布清单的基线是否一致；
8. 客户/系统负责人是否需要批准需求或接口变更。

**关闭条件：** 变更已批准；受影响工作产品已更新；验证与回归结果满足判定准则；缺陷已处置；配置基线和交付信息已同步。

## 5. 项目会议与节奏建议

| 节奏 | 会议/活动 | 必须输出 |
|---|---|---|
| 每周 | 项目状态与风险评审 | 进度偏差、风险变化、行动项和升级决策 |
| 每个关键工作产品 | 技术/需求/架构评审 | 评审对象版本、发现项、结论和关闭记录 |
| 每次正式变更 | 变更影响分析与批准 | 影响范围、批准人、验证计划和基线更新 |
| 每次构建/测试里程碑 | 配置与验证检查 | 被测版本、环境、测试结果、未关闭问题 |
| 每个里程碑 | QA 过程检查 | 发现项、整改期限、复核与关闭证据 |
| 发布前 | 发布就绪评审 | 基线清单、测试摘要、已知问题、批准与交付记录 |

## 6. SUP / MAN 常见反模式

- 项目计划只列日期，没有交付物、依赖、责任人和完成判据；
- 风险清单长期不更新，或风险没有可执行措施；
- QA 只在评估前临时检查；
- 缺陷只记录“已修复”，没有修复版本和回归结果；
- 变更未经影响分析就直接改代码；
- 测试报告和交付代码不是同一个基线；
- 配置管理只管源代码，不管参数、工具链、测试环境和报告；
- 行动项没有责任人、期限和关闭证据。

## 7. 可复制的管理记录模板

### 风险/问题记录
| ID | 类型 | 描述/影响 | 优先级 | 措施 | 责任人 | 到期日 | 状态/证据 |
|---|---|---|---|---|---|---|---|
| RISK-001 | 风险 | 示例：测试台架交付可能延迟 | 中 | 准备仿真环境并确认交付节点 | 负责人 | YYYY-MM-DD | Open / 链接 |

### 变更记录
| 字段 | 填写内容 |
|---|---|
| CR ID / 标题 | 唯一编号和简明描述 |
| 提出人 / 日期 | 变更提出者和日期 |
| 变更原因 | 缺陷、客户要求、设计改进或法规变化 |
| 影响范围 | 需求、架构、代码、硬件、参数、测试、交付物 |
| 风险与资源影响 | 安全/质量/进度/成本/资源影响 |
| 评审与批准 | 评审结论、批准人和日期 |
| 验证策略 | 新增/修改的测试与回归范围 |
| 基线更新 | 相关配置项、版本和发布信息 |
| 关闭证据 | 验证结果、缺陷关闭、复核人和日期 |

## 8. 项目落地检查清单

- [ ] 项目计划有基线、责任人、依赖和可测量完成判据
- [ ] 风险和问题分开管理，状态定期更新
- [ ] QA 检查计划覆盖关键过程与工作产品
- [ ] 发现项有客观证据、责任人、期限、复核与关闭依据
- [ ] 配置项、基线和访问/变更规则明确
- [ ] 构建和测试报告能定位准确的代码、参数、工具与环境版本
- [ ] 每次变更均有影响分析、评审批准、回归验证和基线更新
- [ ] 发布清单与实际交付物、测试证据一致
- [ ] 行动项和决策有记录且可追踪
