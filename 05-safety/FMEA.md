# 功能安全与失效分析

状态：Draft（不是安全论证或项目安全结论）

## 1. 分析层次
应区分故障（Fault）、错误（Error）、失效（Failure）和危险（Hazard）。实际项目术语应以适用标准及组织定义为准。

## 2. FMEA 的基本结构
| 字段 | 应回答的问题 |
|---|---|
| 功能/项目 | 正常情况下系统要做什么？ |
| 失效模式 | 功能如何失效？ |
| 失效原因 | 什么机制导致失效？ |
| 局部影响 | 本模块发生什么？ |
| 系统影响 | 对上层系统/车辆有什么影响？ |
| 检测手段 | 如何发现失效？检测时间多长？ |
| 现有控制 | 设计预防、诊断和验证措施是什么？ |
| 改进措施 | 如何降低发生、提升检测或限制后果？ |
| 证据 | 分析、试验、数据或评审记录在哪里？ |

RPN、严重度/发生度/探测度评分方法应采用项目规定的方法，不能在不同评分体系之间直接比较。

## 3. 充电控制场景示例（概念性）
| 失效模式 | 可能影响 | 建议检查 |
|---|---|---|
| 充电电流请求错误 | 可能导致功率目标不正确 | 范围检查、独立限值仲裁、测试边界 |
| BMS 数据过期 | 控制器使用陈旧限制值 | 数据新鲜度、超时监控、降级策略 |
| 接触器反馈与命令不一致 | 实际能量路径与控制状态不一致 | 命令/反馈诊断、超时、停止策略 |
| 通信丢失未被识别 | 系统不能及时进入预期降级/停止行为 | 故障注入、超时验证、日志检查 |
| 故障清除条件过宽 | 故障可能在根因仍存在时复位 | 复位条件审查、故障持续注入 |

这些是分析起点，不是对具体产品风险等级或安全机制充分性的判断。

## 4. 从 FMEA 到验证
1. 明确失效注入方式与前置条件。
2. 记录期望诊断、响应时间和系统状态。
3. 记录实际输出、波形、日志和时间戳。
4. 检查故障是否可检测、响应是否有效、恢复是否受控。
5. 关联需求、设计、软件/硬件版本和测试结果。
6. 若结果不符合预期，更新分析并追踪整改闭环。

## 5. 与 ISO 26262 工作的接口
视项目范围与安全生命周期要求，相关工作可能包括 HARA、安全目标、功能/技术安全概念、安全需求分解、验证确认及安全分析。FMEA 不能替代 HARA，也不能仅凭一张表判定 ASIL 或证明安全。

## 6. 评审问题
- 失效模式是否覆盖正常、边界、启动、停止和恢复场景？
- 是否区分故障原因与失效表现？
- 影响是否沿接口和系统边界传播分析？
- 检测机制是否有时间预算和验证证据？
- 安全状态是否定义明确且可测量？
- 是否分析共因、潜伏故障及诊断失效（如适用）？
- 整改后是否有回归验证和变更追溯？

## 7. 项目需补充
适用标准版本、HARA/安全需求编号、系统边界、故障模型、项目评分方法、审核记录和测试证据。
