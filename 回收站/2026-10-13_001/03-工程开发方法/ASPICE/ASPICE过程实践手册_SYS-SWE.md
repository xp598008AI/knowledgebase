# ASPICE 过程实践手册：SYS / SWE

> 状态：Draft / 项目实施参考  
> 适用：汽车电子 ECU、EVCC、OBC、DCDC、BMS 等系统与嵌入式软件开发。  
> 使用前提：先确认客户要求、项目采用的 Automotive SPICE PAM/PRM 版本及评估范围。下文按 ASPICE 4.0 常见过程命名进行实践化整理，不是标准原文或完整 Base Practice 清单。

## 1. SYS 与 SWE 的边界

- **SYS（系统工程）**：将利益相关方需求转化为系统需求，定义系统架构，并验证系统需求、集成结果和系统行为。
- **SWE（软件工程）**：承接分配给软件的系统需求，形成软件需求、软件架构、详细设计与实现，并进行分层验证。
- **关键接口**：系统架构将需求分配给硬件、软件、机械、通信或外部系统；软件团队不能自行假定未分配的系统行为。
- **跨层闭环**：需求必须可追溯到设计与测试；验证失败必须进入问题解决流程，修复后执行影响分析和回归验证。

## 2. SYS 过程实践

### SYS.1 — Requirements Elicitation（需求获取）

**目的：** 从利益相关方识别并理解需求、期望、约束和使用场景。

**输入示例**
- 客户需求、法规/标准约束、系统接口约束；
- 使用场景、市场需求、运行环境、已有产品问题；
- 供方/客户澄清记录。

**活动建议**
1. 识别利益相关方与需求来源，建立来源 ID。
2. 组织需求访谈、场景分析、接口澄清和冲突协商。
3. 记录假设、约束、未决问题及其责任人。
4. 与利益相关方确认需求理解，记录确认结论和变更。

**典型工作产品**
- 利益相关方需求清单/规格；
- 需求来源与决策记录；
- 未决问题和假设清单；
- 评审/确认记录。

**评审检查**
- 每条需求是否有来源、唯一 ID 和责任方？
- 需求是否可理解、可追踪，且与场景关联？
- 冲突、假设、接口边界是否显式记录？
- 是否有确认结论，而非仅有会议纪要？

### SYS.2 — System Requirements Analysis（系统需求分析）

**活动建议**
1. 将利益相关方需求分析为可验证的系统需求。
2. 定义触发条件、输入、输出、约束、时序、异常行为和验收准则。
3. 检查完整性、一致性、可行性、可验证性及双向追溯。
4. 分析安全、诊断、网络安全、法规和环境约束（按项目适用性）。

**典型工作产品**
- 系统需求规格；
- 需求属性/状态；
- 需求验证准则；
- 需求追溯关系；
- 需求评审记录与问题清单。

**常见缺陷**
- “快速、稳定、可靠”等无法验证的形容词；
- 把设计方案写成需求，却没有说明必要约束；
- 缺少异常路径、边界条件和恢复行为；
- 需求之间冲突，或需求没有验证方法。

### SYS.3 — System Architectural Design（系统架构设计）

**活动建议**
1. 定义系统元素及其职责和边界。
2. 将系统需求分配给系统元素，明确硬件、软件、外部系统的分工。
3. 定义接口、数据流、控制流、时序、供电/诊断/通信约束。
4. 评估架构方案，记录关键设计决策与权衡。
5. 将架构元素和接口追溯回相关需求。

**典型工作产品**
- 系统架构图；
- 系统元素/需求分配矩阵；
- 接口控制文件（ICD）或接口规格；
- 架构决策记录；
- 架构评审记录。

**评审检查**
- 每条系统需求是否已分配或有明确理由未分配？
- 接口是否定义方向、单位、范围、时序、错误处理和责任方？
- 软硬件边界是否清楚？跨控制器状态/超时/复位行为是否一致？
- 关键架构决策是否有依据和影响分析？

### SYS.4 — System Integration and Integration Verification（系统集成与集成验证）

**活动建议**
1. 制定集成顺序、环境、接口验证策略和准入准出条件。
2. 按系统元素集成计划组装系统。
3. 验证接口、交互、数据/控制流及异常处理。
4. 记录环境、配置、结果、偏差和缺陷。
5. 缺陷修复后评估回归范围，并保留重新验证结果。

**典型工作产品**
- 系统集成计划；
- 集成测试规范/用例；
- 集成环境与配置记录；
- 测试结果、日志、问题记录。

### SYS.5 — System Verification（系统验证）

**活动建议**
1. 从系统需求的验收准则推导系统验证用例。
2. 明确测试环境、版本、数据、设备校准/配置及判定规则。
3. 执行测试并记录通过、失败、阻塞和偏差。
4. 分析需求覆盖、未验证需求和失败项处置。
5. 确保报告关联被测系统的准确基线。

**典型工作产品**
- 系统验证策略/计划；
- 系统验证规范和用例；
- 需求覆盖矩阵；
- 测试报告、缺陷与回归证据。

> 验证（Verification）回答“工作产品是否满足规定要求”；确认（Validation）通常更关注产品是否满足预期用途/利益相关方需要。具体术语按项目适用模型和客户要求统一。

## 3. SWE 过程实践

### SWE.1 — Software Requirements Analysis（软件需求分析）

**输入：** 分配给软件的系统需求、系统接口、平台/硬件约束、客户特定要求。

**活动建议**
1. 分析并细化软件应提供的功能、性能、诊断、接口和异常行为。
2. 定义软件需求的触发条件、状态、时序、输入/输出和可验证判据。
3. 检查需求冲突、重复、隐含依赖及资源约束。
4. 建立系统需求到软件需求的双向追溯，并评审确认。

**典型工作产品：** 软件需求规格、需求属性、追溯矩阵、评审记录、未决问题。

### SWE.2 — Software Architectural Design（软件架构设计）

**活动建议**
1. 将软件需求分配到软件组件/层/任务。
2. 定义组件职责、接口、依赖、运行时交互、数据所有权和调度约束。
3. 定义错误处理、超时、重试、复位、降级和诊断策略。
4. 评估关键架构约束与非功能需求，形成设计决策记录。
5. 保持需求—架构元素—接口的追溯关系。

**典型工作产品：** 软件架构、组件/接口定义、数据流/状态机/时序图、架构评审记录。

### SWE.3 — Software Detailed Design and Unit Construction（软件详细设计与单元构建）

**活动建议**
1. 将架构组件细化为可实现、可验证的软件单元。
2. 定义接口契约、状态迁移、算法、数据结构、错误码和边界行为。
3. 按编码规范实现，执行代码评审和静态检查。
4. 维护设计、代码提交、构建配置之间的版本关联。
5. 对复杂逻辑补充设计说明和测试设计依据。

**典型工作产品：** 详细设计、源代码、代码评审记录、静态分析结果、构建/配置说明。

### SWE.4 — Software Unit Verification（软件单元验证）

**活动建议**
1. 基于单元设计和相关软件需求设计单元测试。
2. 覆盖正常路径、边界值、错误输入、异常路径和状态迁移。
3. 定义测试桩/驱动、环境、判定准则及覆盖目标（按项目要求）。
4. 记录执行结果、问题和修复后的回归结果。
5. 将测试结果关联到被测单元、代码版本和测试环境。

**典型工作产品：** 单元验证规范、用例、环境配置、执行日志、覆盖报告、缺陷记录。

### SWE.5 — Software Integration and Integration Verification（软件集成与集成验证）

**活动建议**
1. 按架构依赖和集成策略规划集成顺序。
2. 验证组件间接口、调用顺序、数据一致性、时序和错误传播。
3. 覆盖初始化、并发/任务调度、超时、资源不足和恢复路径（按适用性）。
4. 记录集成环境、版本、结果和缺陷。
5. 修复后执行有依据的回归测试。

**典型工作产品：** 软件集成计划、接口测试规范、集成日志、问题记录、回归结果。

### SWE.6 — Software Verification（软件验证）

**活动建议**
1. 从软件需求和验证策略推导软件验证用例。
2. 在目标环境、仿真环境或约定的集成环境中验证软件行为。
3. 检查需求覆盖、接口行为、异常处理和非功能约束。
4. 记录软件版本、配置、环境、数据、结果和偏差。
5. 对失败项形成缺陷闭环，并判断是否需要系统级回归。

**典型工作产品：** 软件验证规范/用例、需求覆盖矩阵、测试报告、缺陷与回归证据。

## 4. 示例：EVCC 充电通信超时功能端到端追溯

> 以下是教学示例。超时值、状态机行为及诊断要求必须由项目需求、适用协议和安全分析确定。

| 层级 | 示例 ID | 示例内容/工作产品 |
|---|---|---|
| 利益相关方需求 | STK-REQ-010 | 充电通信异常时系统应按定义策略退出或恢复 |
| 系统需求 | SYS-REQ-042 | 指定通信阶段在规定时限内未收到有效响应时，系统进入定义的异常处理路径 |
| 系统架构 | SYS-ARCH-IF-07 | EVCC 通信管理、计时器服务、诊断服务之间的接口和职责 |
| 软件需求 | SWE-REQ-118 | 软件应在状态进入时启动对应计时器，并按规定条件判定超时 |
| 软件架构/详细设计 | SWE-DES-031 | 状态机迁移、计时器生命周期、取消条件、重复响应处理 |
| 实现 | COMMIT/BUILD ID | 实际代码提交和可复现构建标识 |
| 单元验证 | UT-CASE-201… | 正常响应、边界前/边界/边界后、无效响应、重复响应 |
| 集成验证 | IT-CASE-087 | 通信模块与状态管理、诊断模块交互验证 |
| 软件/系统验证 | SV-CASE-054 | 在目标配置下验证端到端异常路径 |
| 问题与变更 | BUG/CR ID | 失败现象、根因、影响范围、修复版本、回归结果 |

### 示例评审问题
- 需求的“规定时限”是否有唯一、受控的参数来源？
- 计时器在状态退出、重入、复位和重复消息时如何处理？
- 边界时间的判定语义是否明确且测试可复现？
- 软件需求是否覆盖诊断记录、恢复策略和错误传播？
- 测试报告能否定位到准确的代码/软件版本和环境？
- 修改计时器服务后，哪些状态机、诊断及系统测试需要回归？

## 5. SYS/SWE 评审会议的最小输出

每次正式评审至少记录：
- 评审对象名称、版本/基线、日期和参与角色；
- 评审准入条件与使用的检查表版本；
- 发现项 ID、描述、严重度、责任人和截止日期；
- 评审结论：通过、带条件通过或退回（按项目规则定义）；
- 发现项关闭证据、复核人和关闭日期；
- 与需求、设计、代码、测试及变更单的关联。

## 6. SYS/SWE 常见反模式

1. **先写测试再补需求**：测试结果无法证明需求完整性；应从受控需求与验收准则导出测试。
2. **架构图只有方框**：缺少职责、接口、数据/控制流、时序和异常语义。
3. **需求追溯只做单向**：无法发现未被实现的需求或无需求来源的设计。
4. **测试报告不含版本信息**：即使通过也无法证明被交付版本满足要求。
5. **集成成功即认为验证完成**：集成正常不等于所有需求、边界和异常路径已验证。
6. **变更只改代码**：必须分析受影响需求、设计、测试、配置基线和交付文档。

## 7. 项目启动时的 SYS/SWE 最小交付包

- [ ] 系统/软件需求规格与需求属性规则
- [ ] 需求来源、分配和双向追溯矩阵
- [ ] 系统架构、软件架构和关键接口定义
- [ ] 详细设计及设计评审记录
- [ ] 单元、集成、软件/系统验证策略
- [ ] 测试规范、用例、环境和版本记录
- [ ] 测试报告、覆盖分析和缺陷闭环
- [ ] 变更影响分析与回归验证记录
- [ ] 受控基线与发布清单
